# Batch 0010: the Rust that Burn generates from SmolLM2's ONNX graph

- **Registered:** 2026-10-06, before any cell ran.
- **Kind:** a calibration (an instrument check: a second program that runs
  SmolLM2-135M-Instruct, generated from the graph rather than interpreting
  it), with one description cell (the generated source).
- **Status:** run once; results below. Tables in `0010/`.
- **Branch:** `batch/0010-onnx-to-rust`, on top of batch 0008.
  **Workflow:** `.github/workflows/batch-0010.yml`. **Code, registered:**
  `batches/0010/nodes.py` (1,226 bytes), `logits.py` (1,273), `compare.py`
  (1,351), `burn.sh` (2,264), `runner/src/main.rs` (2,265),
  `runner/Cargo.toml` (742); data: `prompts.txt` (117). **Code, written after
  the data:** `align.py` (1,408), `tally.sh` (1,344).
  **Depends on:** batch 0002 (the published graph's operators; Optimum's own
  comparison of its export with PyTorch, 3.0e-4 on the logits), batch 0003
  (the prompt, its token ids, the five next-token numbers of PyTorch and of
  ONNX Runtime on three graphs), batch 0006 (the operator census of
  Optimum's export of SmolLM2).

## Purpose

Batch 0003 found that three ONNX graphs of SmolLM2 compute one next-token
distribution to four decimals, in four programs. Each of those programs
interprets a graph. `burn-onnx` does something else: it reads the graph and
writes Rust source, a `Model` struct with a typed `forward` and a weights
file, in which each ONNX node has become a statement. The graph then exists
as text in a language with a type checker, and a program that runs the model
exists that can be read line by line. R3 asks how equality of two forms is
decided; a form that is source text can be compared as source text, as well
as by what it computes. This batch makes that form, runs it, and asks only
whether it computes what ONNX Runtime computes on the same file. The
comparison of the generated source with any other Rust program is a later
batch's.

No LARQL code, text or data is used in this batch.

## The claim it would license, and nothing more

If the predictions below hold, the Rust that `burn-onnx` generates from
Optimum's export of SmolLM2-135M-Instruct may be used as a baseline readout
of that model, next to PyTorch, ONNX Runtime and llama.cpp, and the
generated source may be read as a statement of what the graph computes. It
licenses nothing about other models, other graphs of this model (the
published graph declares operators outside ONNX), padded or cached inputs,
or any other Rust program.

## Cells

- **01 (two models, in parallel).** Optimum exports each model without past
  (`optimum-cli export onnx --task text-generation`, as batch 0006). The
  checker is run on it. The graph is written as text, one row per node
  (`nodes.py`). The prompts of `prompts.txt` are tokenised by the model's own
  tokenizer. ONNX Runtime writes the logits of every position of each prompt,
  with graph optimization on and with it off. `compare.py` is run on logits
  with one value moved by 0.5, which it must report. The models: a tiny random
  Llama (`hf-internal-testing/tiny-random-LlamaForCausalLM`, hidden size 16,
  two layers), which is the smoke for everything after it and carries no
  claim, and SmolLM2-135M-Instruct.
- **02 (one job).** `onnx2burn` is built from the head of burn-onnx's
  default branch (its workspace lock, Burn at the revision that lock names).
  For the tiny graph and, only if that ran, for SmolLM2's: `onnx2burn`; the
  generated Rust and `runner` built with `cargo build --release`, Burn's
  `flex` backend; the logits of every position written; both compared with
  ONNX Runtime's. Then the published `onnx/model.onnx` is given to
  `onnx2burn`.

The prompts, three, all read as raw continuations: `The capital of France is`
(batch 0003's, five tokens), `Paris` (one or two), and a sentence of about
seventeen tokens that ends in the same prompt.

## Predictions, with severity

- **P1, moderate severity.** `onnx2burn` converts both graphs and the
  generated Rust builds with `flex`. Refuted by an error from either tool. A
  refutation lands first on onnx-ir's handling of symbolic dimensions and of
  the operators of the census, and then on the build time or memory of a
  graph of about 7,400 nodes.
- **P2, high severity.** For each prompt, the five most probable next tokens
  from the Rust are the same ids in the same order as ONNX Runtime's on the
  same graph, and each of the five probabilities differs by at most 1e-4.
  For the first prompt the five are batch 0003's, at four decimals: ` Paris`
  0.4693, ` the` 0.2658, ` located` 0.0832, ` called` 0.0175, ` Le` 0.0149.
  Refuted by another order or a larger difference. It would fail if any
  operator in the path were wrong: the mask, the softmax, the rotary
  slicing, a cast.
- **P3, moderate severity.** The largest absolute difference of logits, over
  every position of every prompt and the whole vocabulary, is at most 1e-3.
  The bound is a little above batch 0002's 3.0e-4 between Optimum's export
  and PyTorch, because the Rust uses other matrix kernels than ONNX Runtime.
  Refuted by a larger difference. If P2 holds and P3 fails, the difference
  is numeric; where it enters is a later batch's question.
- **P4, moderate severity.** One generated model serves the three prompts
  without a second import: P2 and P3 hold for each length. Refuted if a
  length errors or breaks P2. The importer's documentation says concrete
  dimensions baked into a file are trusted, and an export could bake one.
- **P5, a control, low severity.** ONNX Runtime with graph optimization on
  and with it off give the same five tokens in the same order, and logits
  within 1e-4. Refuted if not: then ONNX Runtime's answer depends on its
  optimization, and the reference is to be stated with its setting.
- **Control of the instrument.** `compare.py`, given logits with one value
  moved by 0.5, reports a largest difference of 0.5. Refuted if it does not.
- **Observed, no prediction.** The generated source: its bytes, lines and
  the statements by method (what each ONNX operator became); whether
  attention was fused into one `attention` call; whether the graph was split
  into submodules. The peak memory and time of `onnx2burn`, of each build and
  of a forward pass. And the published graph through `onnx2burn`, where the
  expectation from Burn's own table of supported operators is a stop at the
  vendor-domain operators that batch 0002 counted in it (1
  `SimplifiedLayerNormalization`, 60 `SkipSimplifiedLayerNormalization`, 30
  `GroupQueryAttention`); a conversion that succeeds would refute that.

## Auxiliaries

What a refutation could land on instead of the Rust itself, and which would
be blamed first:

- onnx-ir's shape and type inference, and its simplification passes (they
  rewrite the graph before any code is written);
- the exporter's version and options (recorded; the graph differs between
  versions, which batch 0003 found for three producers);
- ONNX Runtime's graph optimization (P5);
- Burn's `flex` kernels: its matrix multiply, and its boolean operations
  (issue 4771, closed 2026-04-13, was a broadcast fault in them; Burn's own
  SmolLM2 check was flagged blocked on it and the flag may be stale);
- integer dtypes: the runner gives `Int` tensors made from 32-bit integers
  where the graph says int64;
- the runner's glue: the order of the three inputs (given by the graph) and
  the all-ones mask;
- `compare.py` (its control above).

## Rivals to exclude

- **A shared misreading of the graph.** Agreement of the Rust with ONNX
  Runtime would not show the graph is read correctly if both misread it the
  same way. Batch 0003 excludes it for ONNX Runtime: on Optimum's graph it
  gave PyTorch's and llama.cpp's five numbers.
- **Agreement on one length only.** The prompts have three lengths.
- **Agreement on the last position only.** The logits of every position are
  compared.
- **A reference that depends on optimization.** P5.
- **Not excluded:** padded inputs (the mask is all ones throughout), cached
  inputs (the graph has no past), other models, other graphs.

## Results

### Run: 2026-10-06

Workflow run [37462129427](https://github.com/metavacua/lm-normal-form/actions/runs/37462129427),
every cell, the status report successful. The outcomes below are read from
the workflow's own record of each observation (`outcomes.json`), not from the
step list. Runner: AMD EPYC 9V74, four vCPUs. rustc 1.99.0; burn-onnx at
`1c6cdef` (the head of its default branch that day), Burn at `00a9db7` (the
revision burn-onnx's workspace names); torch 2.14.1, transformers 4.57.6,
optimum 2.1.0, onnx 1.23.2, onnxruntime 1.30.0. SmolLM2-135M-Instruct at
`12fd25f`. Tables in `0010/`.

**The graph.** Optimum's export of SmolLM2-135M-Instruct, opset 18: 7,360
nodes, 273 initializers of 162,826,560 elements, three inputs
`input_ids`, `attention_mask`, `position_ids` of shape
`[batch_size, sequence_length]` and the output `logits`. The operators are the
census of batch 0006 (which counted 7,361 nodes and 152 `Transpose` by
graphsurgeon; `nodes.py` counts 7,360 and 151) and six that its census did not
name (`Range` 3, `And` 2, `LessOrEqual` 1, `Flatten` 1, `Cos` and `Sin` 1 each). The
elements exceed batch 0003's header count (134,515,008) by 28,311,552, which
is 49,152 × 576: the tied embedding, stored a second time transposed for the
head. The tiny random Llama: 436 nodes, 17 initializers, 1,032,208 elements.

**ONNX Runtime alone (P5 and the control).** The first prompt's five most
probable next tokens, ids 7042, 260, 3807, 1217, 2250, have probabilities
0.4693, 0.2657, 0.0831, 0.0175, 0.0149 (graph optimization on) and 0.4693,
0.2657, 0.0832, 0.0175, 0.0149 (off); batch 0003's PyTorch gave 0.4693, 0.2658,
0.0832, 0.0175, 0.0149. With optimization on and off the logits differ by at
most 4.4e-5, 1.1e-5 and 4.1e-5 over the three prompts, the top five keep their
order, and no probability moves by more than 1.1e-6. Given logits with one
value moved by 0.5, `compare.py` reports a largest difference of 0.5 on both
models.

### The predictions

- **P1 met.** Both graphs converted and both generated programs built, with
  no error.
- **P2 met, with a margin of about 100.** Same ids, same order, for every
  prompt against both settings; the largest probability difference is 1.1e-6
  against a bound of 1e-4.
- **P3 met, with a margin of about 13.** The largest logit difference is
  7.7e-5 against 1e-3. It is of the size of ONNX Runtime's own difference
  between its two settings (4.4e-5): the Rust is about as far from ONNX Runtime
  as ONNX Runtime is from itself under a flag.
- **P4 met.** One model, three lengths, one import.
- **P5 met.** 4.4e-5 against 1e-4, order kept.
- **Control met.**
- **Observed.** The published graph stops where Burn's table of supported
  operators said it would, with one operator the registration did not list:
  `RotaryEmbedding`, 60 nodes, one each for q and k in each layer. Burn's
  xtask marks its SmolLM and SmolLM2 checks `blocked: true`, with the comment
  that their attention-mask `And` path hits an out-of-bounds in
  `bool_and_inplace_u8` (issue 4771) and that they are to be unblocked "when a
  burn rev bump brings in the fix". The issue is closed and the revision built
  here has the fix (its `bool.rs` broadcasts both operands before dispatch).
  This graph builds its mask with `And` on broadcast operands (one `bool_and`
  statement) and ran correctly, so the flag looks stale at this revision.

### Findings beyond the predictions (post-designated: the code is `align.py` and `tally.sh`, written after the data)

- **The generated source is a transcription, node for node.** Of 7,360 nodes
  there are 4,800 `let` statements (the Constant nodes are lifted into the
  operators, folded, or kept as `Param` fields), 211 `Linear` fields (30
  layers × 7 projections + the head), 916 `Param` fields, 32 submodules and no
  call to Burn's fused `attention`. (From its source, onnx-ir's attention fusion
  needs the softmax output to feed a single `MatMul`; here it feeds `IsNaN` and
  `Where`. Read, not tested.) onnx-ir names each statement `<operator><ordinal among the
  nodes of that operator, in file order>` and a MatMul with a weight
  `linear<k>`; with that rule every node of layer 0 was found in the Rust
  (`0010/layer0-onnx-to-rust.txt`). There is no persisted map from ONNX
  names to generated names; the rule is how to recover one.
- **RMSNorm, rotary embedding, attention and SwiGLU are visible in the Rust as
  they are in the graph.** RMSNorm is `powf`, `mean_dim(2)`, `add`, `sqrt`,
  `div`, `mul`, `mul`; the two float32-to-float32 `Cast`s of each have no
  statement; ε, the exponent 2 and 1.0 are one-element tensors in the weights
  file, broadcast by `unsqueeze_dims`. The rotary embedding is `slice`, `neg`,
  `Tensor::cat([neg(second half), first half])`, `mul`, `add`: the second half
  of each head, negated, placed before the first. The scores are `mul(q, c)`, `mul(kᵀ, c)`, `matmul`; then the mask by
  `mask_where` and `add`, `softmax(·, 3)`, `is_nan`, `mask_where`, `matmul`.
  SwiGLU is `Linear`, `sigmoid`, `mul`, `Linear`, `mul`, `Linear`.
- **The next-token head is one node.** The graph ends with the final RMSNorm
  (nine nodes, the same as each layer's) and `/lm_head/MatMul`, whose weight
  is the transposed embedding: 28,311,552 of the graph's 162,826,560
  initializer elements. Everything before them is the stack. The causal mask
  is a separate subgraph of about forty nodes built once under `/model`
  (`Range`, `LessOrEqual`, `And`, `Flatten`, `Gather`, `Expand`) and cut
  to length in each layer by a `Slice` and a `Where`.
- **Shapes are handled at run time.** The importer keeps the symbolic
  dimensions out of the types (the generated `forward` takes ranks only);
  shape arithmetic becomes host arrays (`[i64; N]`) and some reshapes read the
  device (`to_data()`), which is cheap on a CPU backend and would not be on a
  GPU one.

### Limits

One run: the run-to-run floor is not measured here (the processor and the
revision of both tools are recorded). One model, on a CPU, in float32, with no
padding in the mask and no cache in the graph. The tiny model's weights are
random and it carries no claim. The comparison is of logits: no per-layer
quantity has been compared, so where a larger difference would enter, had
there been one, is not known. No other Rust program has been compared with
this one; that is for a later batch, and nothing from LARQL is used here.
