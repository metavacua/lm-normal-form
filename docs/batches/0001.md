# Batch 0001: structure graphs of twelve published ONNX files

- **Registered:** 2026-10-05, before any cell ran.
- **Status:** not yet run. Results are appended below once CI has produced them.
- **Branch:** `batch/0001-structure-graphs`. **Cells:** `batches/0001.json`.
- **Code:** `src/lmnf/experiments/structure.py`, `src/lmnf/`, `queries/`.

## Purpose

LARQL has shown that a transformer language model can be turned into a
graph-shaped index and that inference can run over it. This batch does not
test whether that is possible.

It builds and checks the first stage of a general extractor: the
operator-level structure of a published computation graph, held as RDF in a
standard graph database. The checks below are acceptance checks on that
stage. They say whether the extraction is faithful for a given file, across
precisions, quantised forms and three model families.

## Cells

Twelve published files, one job each. Every cell uses the prompt
`The capital of France is`.

- **01 to 08.** The eight ONNX files of `HuggingFaceTB/SmolLM2-135M-Instruct`:
  full precision (`model.onnx`), half precision (`model_fp16.onnx`) and six
  quantised forms (`q4`, `q4f16`, `bnb4`, `int8`, `uint8`, `quantized`). One
  set of weights, eight files.
- **09.** `HuggingFaceTB/SmolLM2-360M-Instruct`, `onnx/model.onnx`: the same
  family at other dimensions.
- **10 and 11.** `openai-community/gpt2`, `onnx/decoder_model.onnx` and
  `onnx/decoder_model_merged.onnx`: another architecture. A merged decoder is
  made by putting two graphs behind an `If` node, so cell 11 is where H1 is
  expected to fail.
- **12.** `onnx-community/Qwen3-0.6B-ONNX`, `onnx/model.onnx`: a third family.
  Its tensors are in a companion file, and its PyTorch weights are in another
  repository (`Qwen/Qwen3-0.6B`).

## Method

Nothing in this repository implements a model. Graphs are read by the
reference `onnx` package; forward passes are run by ONNX Runtime and by
PyTorch through `transformers`.

1. Fetch the file at the revision published when the job starts. Record the
   revision and the file's SHA-256. Models are not pinned: a later revision
   that changes an outcome is a finding.
2. Run the `onnx` checker on the file.
3. Take a report straight from the ONNX model: nodes, operators, graph-valued
   attributes, node order, stored tensors.
4. Write the same structure as RDF (N-Quads, one named graph per file). Tensor
   contents are not written; each stored tensor is described by type, shape,
   size and SHA-256. Small tensors whose values are structure (shapes, axes,
   scalar constants) are written out.
5. Load the RDF into Oxigraph and ask the questions of step 3 again in SPARQL.
6. Compare the stored tensors with the parameter list in the header of the
   reference repository's `model.safetensors`.
7. Run the prompt through the graph with ONNX Runtime and through the
   reference weights with `transformers`, and compare the next-token
   distributions.

## Premises

A premise that fails makes the cell **inconclusive**. An inconclusive cell
exits with status 2 and its job fails.

- **P1.** The `onnx` checker accepts the file.
- **P2.** The graph is not empty.
- **P3.** SPARQL over the RDF and the direct report agree exactly on node
  count, operator histogram, number of control-flow nodes, the node-order
  check, undefined inputs, and the count, element total and byte total of
  initializers. The number of quads written equals the number stored.
- **P4.** Every check below could be evaluated.

## Checks

A check that fails is a result. It does not fail the job. The checks keep the
labels H1, H2 and H5 that the reports use.

- **H1. The forward pass has no control flow and no cycle.**
  Holds when no node carries a graph as an attribute (`If`, `Loop`, `Scan` and
  the like), no value is consumed at or before the position of the node that
  produces it, no input is undefined, and model-local functions do not call
  one another in a cycle. If no value is consumed at or before its producer,
  node order is a topological order, so the graph is acyclic; the check needs
  no recursion.
- **H2. Every parameter is stored in the graph.**
  Holds when each tensor listed in the safetensors header has a floating-point
  stored tensor of the same shape in the graph, counted with multiplicity. A
  stored tensor is an initializer or the value of a `Constant` node. A matrix
  matches its transpose, because an exporter may store a linear layer either
  way round. Tensors the graph stores beyond the reference are counted and do
  not count against it.
- **H5. The graph computes what the PyTorch weights compute.**
  Under the tokenizer's default encoding of the prompt: the five most probable
  next tokens are the same, in the same order, and no probability differs by
  more than 1e-3.

  The same comparison is recorded, without a verdict, with the BOS token
  prepended when the tokenizer has one and does not add it. Implementations
  differ on that choice.

The graph is fed from its own declared inputs: token ids, an attention mask
of ones, positions counted from zero, and an empty past whose shape is read
from the graph. An input these rules do not cover is not guessed at; the cell
is inconclusive and names it.

## Expected

Cell 11 is expected to fail H1, because a merged decoder is built with an
`If` node. The quantised files 03 to 08 are expected to fail H2 and H5,
because their weights are stored as integers or packed blocks and they
compute a slightly different function. A failure anywhere else points at the
extractor or at the file and needs explaining.

## Recorded without a verdict

- How many stored matrices match "a matrix product whose result is multiplied
  by its own sigmoid" (`queries/silu_gate.rq`).
- How many reference tensors are matched when stored tensors of every element
  type are counted, not only floating-point ones.
- What each job used: peak memory, time and disk, measured on the runner.

## Next stage, not in this batch

The architecture schema: layers, heads, dimensions and the role of every
tensor. These are not to be rediscovered from wiring. The libraries that
define architectures already state them (`transformers`: the configuration
and the module tree). The plan is to take the schema from the library and
join it to the tensors of the graph by content hash, which this batch already
records for every stored tensor.

## What was seen before registration

- Through the Hugging Face API: the file lists and sizes of the repositories
  above, and the safetensors header of `SmolLM2-135M-Instruct` (272 tensors,
  134,515,008 elements, six distinct shapes).
- No ONNX file of any cell has been opened.
- The tooling has run only on small synthetic graphs.

## What this does not establish

- That any of these graphs is a normal form. Two exporters can produce
  different graphs for the same model; nothing here compares exporters.
- That agreement on one prompt is agreement in general.
- That a tensor with the right shape holds the right values. H2 compares
  shapes; H5 is the only check on values, and it is indirect.
- Anything about models whose files are not in the list above.
