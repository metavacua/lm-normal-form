## Purpose

Batches 0003 and 0010 found that several programs, and a Rust program generated from the graph, compute one
next-token distribution from SmolLM2's weights held in different files. Those batches compared what the files
compute. They did not compare what the files hold. Whether the weights are the same set of tensors in each, or
only equivalent in effect, decides what a claim made about one file says about another, and what a graph
database of a model may call the same model.

Two ideas shaped the question. In the Unison language a definition's identity is a hash of its structure with
identifiers removed, and names are metadata kept beside it; the same hash follows the definition across every
rename. For a model's weights the analogue is a hash of each tensor's dtype class, shape and values, with names,
container and layout as labels. And in storage formats a version number is a contract only where a reader checks
it, which is the question of a later batch; here the record that carries the hashes is itself declared as an
interface with a header, verdicts and a fixture, so that the instrument of this batch is not an exception to the
rule it tests.

No LARQL code, text or data is used in this batch.

## The hypothesis, and what would refute it

**H.** A tensor's identity can be computed from its dtype class, shape and values alone (scheme `lmnf-tensor` 1 of
`docs/interfaces/identity.md`: names, container and, for a matrix, orientation are left out), and under it
SmolLM2-135M-Instruct's weights are the same set of 272 distinct tensors in the Hub's safetensors file, in the
ONNX file Optimum exports from it, and in the burnpack `onnx2burn` writes from that file; the tied embedding is
the only tensor stored twice; and a change of names alone changes no digest.

What the cells observe, derived from H: every initializer of the ONNX file and every tensor of the burnpack that is
at least 256 bytes has a key among the safetensors keys, and the key sets are equal (C1); the pairing of tensors by
content agrees with their pairing by names (C2); file digests differ between the containers while keys agree (C3);
a renaming of the graph leaves keys and logits as they were (C4); and the identity of a bag of tensors does not see
which name holds which tensor, which a labelled root does (C5, the limit of H, stated as a prediction).

H is refuted by an initializer or a large burnpack tensor whose key is not among the safetensors keys, by two
different safetensors tensors paired with one initializer, by a disagreement between the pairing by content and
the pairing by names, or by a renaming that moves a digest or a logit.

## The claim it would license, and nothing more

If the predictions below hold, a record of version 1 identifies the weights of SmolLM2-135M-Instruct by content
across safetensors, ONNX and burnpack, and a claim made about those weights (batch 0010's difference between ONNX
Runtime and the Rust, 7.7e-5) can be kept under `(bag_root, environment)`. It licenses nothing about wiring (which
tensor feeds which operator), about other models, other exporters, weights that differ by a symmetry of the model,
or the Hub's later revisions.

## Predictions, with severity

Severity is how likely a prediction is to fail if H were false; a prediction that would hold whatever the files
hold has low severity, and is a control or an anchor. The numbers come from reading source and from earlier
batches' data; none from hashing the weights.

- **P1, low severity (an anchor).** The Hub's `model.safetensors` is a header of 30,528 bytes, 272 `BF16` tensors,
  no `lm_head.weight`, `__metadata__` equal to `{"format": "pt"}`, 134,515,008 elements, in tensor offsets that are
  contiguous and names in byte order; the sha256 of the downloaded bytes equals the Hub's own, which at revision
  `12fd25f77366fa6b3b4b768ec3050bf629380bac` is
  `5af571cbf074e6d21a03528d2330792e532ca608f24ac70a143f6b369968ab8c`; the first six tensors give the same digest
  through the library. Refuted by any difference (a moved revision voids only the digest's value, and the revision
  is recorded).
- **P2, moderate severity.** `safetensors.torch.save_file` given the 272 tensors and `{"format": "pt"}` writes a
  file with the sha256 of the Hub's. Refuted by any byte of difference.
- **P3, moderate severity.** `transformers` (the version recorded) loading the model in bfloat16 and saving it writes one
  `model.safetensors` with the sha256 of the Hub's, without `lm_head.weight`. Refuted by a second file, a tensor
  `lm_head.weight`, other metadata or any other byte.
- **P4, low severity.** The default load is float32; the saved file has 272 `F32` tensors, 538,060,032 bytes of
  tensor data, a sha256 that differs from the Hub's, a `bag_root` equal to the Hub file's, and every tensor cast back to
  bfloat16 has the original's bytes. Refuted if any of the four fails. (The file digest and the tensor digest part
  here.)
- **P5, moderate severity.** Saved forty times in one process, a one-key metadata gives one byte string and a two-key
  metadata gives at least two. Refuted by forty identical strings with two keys (the order of the keys then does
  not vary through the Python binding).
- **P6, moderate severity.** The library reads each of the four rewritten headers and returns the original's tensors;
  each file has a sha256 other than the Hub's; the sha256 of the bytes after the header equals that of the Hub's
  tensor data. Refuted by any rejection. (The header with spaces before it is the likeliest: the format's
  description says the header begins with `{`.)
- **P7, high severity.** The ONNX file has 273 initializers and 162,826,560 elements; every initializer's key is a
  key of a safetensors tensor; the 273 give exactly 272 distinct keys; the key sets are equal and so are the two
  `bag_root`s; the only safetensors tensor paired with two initializers is `model.embed_tokens.weight`. Refuted by an
  unmatched initializer (the exporter changed a value: a fold, a cast, a rounding), an extra key, or a second
  tensor paired twice.
- **P8, moderate severity.** By the consumers' operators: the 211 initializers that `MatMul` takes as its second
  operand are all *transposed* relative to their safetensors tensors (the 210 linear layers' and the head's against the
  embedding); the one that `Gather` takes as its table (the embedding) and the 61 vectors are *identical*; no
  initializer is `none`, `both` or `other`. Refuted by any other relation.
- **P9, moderate severity.** The pairing by names (the initializer's own name when it is a Hugging Face name; else
  the name of the consuming `MatMul` node, `/model/layers.7/mlp/down_proj/MatMul` becoming
  `model.layers.7.mlp.down_proj.weight`; the head's `lm_head.weight` read as the embedding) agrees with the pairing by
  content for all 273 initializers. Refuted by any disagreement or any initializer without a name.
- **P10, moderate severity.** The burnpack is 651,467,264 bytes; its first ten bytes are `4e525542 0100 8be80000`
  (magic `NRUB`, version 1, a metadata of 59,531 bytes); its data section starts at 59,648 with zeros between; it
  holds 669 tensors, 607 `F32` and 62 `I64`, every descriptor having the four keys `dtype`, `shape`, `data_offsets`
  and `param_id`, no `scalars` key, and `metadata` equal to `{"producer": "burn-onnx"}`; every name matches
  `submodule<N>.constant<N>` or `submodule<N>.linear<N>.weight`; 211 end in `.weight` and none in `.bias`; 273 tensors
  are at least 256 bytes, with 162,826,560 elements between them; 61 are the float32 of `1e-5` in shape `[1]`.
  Refuted by any one of these numbers.
- **P11, moderate severity.** The 273 burnpack tensors of at least 256 bytes are the 273 ONNX initializers one for one,
  all *identical* (Burn keeps a `Linear`'s weight as `[d_input, d_output]`, as ONNX does); each of the 396 smaller
  ones has the key of an ONNX `Constant` node's value, or the same values in another shape (*reshaped*: ONNX's scalar
  `[]` against Burn's `[1]`). Refuted by a large tensor that is not identical, or a small one that is none of these.
- **P12, moderate severity.** Two runs of `onnx2burn` on the same ONNX file give burnpacks of the same size and
  different sha256; the bytes that differ lie before the data section and number between 5,200 and 5,500 (669 random
  `param_id`s of eight bytes); the data sections have the same sha256; the descriptors are equal without their
  `param_id`; the `model.rs` files have the same sha256; the two `bag_root`s are equal. Refuted by two identical
  files (the ids are then fixed, not random), or by any difference in the data section or the Rust.
- **P13, low severity.** If this export's sha256 equals batch 0010's (`7583ca8f…df47`; they are equal when the Python
  packages are), then `model.rs` has batch 0010's sha256 (`2b2c1279…1821`; when burn-onnx is at `1c6cdef7…`), though
  this run passes `--no-development`. Refuted only if the conditions hold and an equality does not.
- **P14, low severity (a control).** The renamed graph passes the checker; its logits for each prompt and each of the
  two optimization settings are byte-identical to the original graph's; the two records have equal key sets and
  equal `bag_root`; the two files have different sha256. Refuted by any logit that differs, by a digest that moved, or
  by equal file digests.
- **P15, low severity (the limit of H).** With layer 0's `gate_proj` and `up_proj` exchanged in a copy of the Hub's
  file, the `bag_root` is the original's, the `labelled_root` is not, and the largest difference of the first prompt's
  logits from the unexchanged model is above 1e-3. Refuted by a changed `bag_root`, an unchanged `labelled_root` or a
  difference of 1e-3 or less.
- **P16, moderate severity (its counts were known from batch 0006; its severity rests on its key set and its logits).** With `accelerate` installed the export has 272 initializers and 7,361 nodes, a sha256
  other than the first export's, a key set equal to the safetensors key set and the first export's `bag_root`; ONNX
  Runtime's logits on it differ from those on the first export by at most 1e-4 with the same top five. Refuted by any
  other count, or by a different key set.
- **P17, low severity.** No tensor of the base model `HuggingFaceTB/SmolLM2-135M` has the key of a tensor of the
  Instruct model. Refuted by one shared tensor (a frozen embedding, for instance).
- **Controls of the instrument.** The fixture and the self-test pass (they are cell 00). Refuted by any failure; then
  no cell is read.
- **Observed, no prediction.** The Hub's ids of ten files at each commit of the two repositories, and which of them
  change when; the repositories that hold the same `model.safetensors`; how many of the published ONNX file's
  initializers are keys of safetensors tensors, and which are not; the time and the peak memory of each tool; the
  tiny model's results (smoke).

## Auxiliaries

What a refutation could land on instead of H, and which would be blamed first:

- the readers: the safetensors header read by hand (checked against the library on six tensors and on the census
  numbers of P1), the burnpack read by the layout of the `burn-pack` crate (checked by the exact file size of P10 and,
  through P11, by the equality of its tensors with the ONNX ones), the ONNX initializers by `onnx.numpy_helper`;
- numpy's widening of bfloat16 and float16, checked in the self-test against the standard-library widening on finite
  values;
- the exporter's version, options and optional packages (P16 observes that `accelerate` changes the graph);
- `onnx2burn`'s simplification and partitioning (names are positional, P9 does not rest on them);
- the name transform of P9, which is a convention of Optimum's node names;
- the Hub (a moved revision, a rate limit), `huggingface_hub`'s answer for a file's ids;
- ONNX Runtime and `transformers` as the engines of P14, P15 and P16.

## Rivals to exclude

- **A key too coarse to mean anything.** The key of a matrix is the same as that of its transpose, so a layer's weight could
  be paired with another layer's transposed tensor. P8 (the relation by role) and P9 (the pairing by names) exclude
  it for this model, and so does batch 0010's agreement of the Rust's logits with ONNX Runtime's.
- **A match by shape or by count.** The key has every value in it; P7 is about values.
- **Agreement of two readers that share a misreading.** The safetensors header has two readers (the hand one and the
  library); the burnpack has one, and its offsets are checked by P10's size and by P11's matches.
- **A result that holds for the exporter's default but not in general.** P16 repeats the export with the optional
  package that changes it; no other exporter is tried.

#### What else was seen

- **The tied embedding is bit-for-bit transposed.** The initializer `onnx::MatMul_9693` is the transpose of
  `model.embed_tokens.weight`, to the last bit; the same holds in the burnpack. The two copies in batch 0010's graph
  are one tensor in two layouts.
- **The ONNX float32 tensors are exact widenings of the BF16 ones**: all 273 initializers equal safetensors tensors
  bit for bit after widening, so Optimum's export changed no value.
- **The generated Rust carries the paths of its files.** This run's `model.rs` differs from batch 0010's in two
  places only: the comment `// Generated from ONNX "<input path>"` and the `from_file("<weights path>")` of the
  default constructor. The run wrote its two outputs to `gen1` and `gen2`, so the sources of the two
  differ for that reason (shown by P18 in run 2). The cost of the refutation is a label the generated Rust bakes
  in: its bytes are a function of where it was generated.
- **`--no-development` leaves out the debug dump and most of the cost**: 7.7 s and 2.1 GB for the generated Rust
  and weights of SmolLM2, against 43 to 57 s and 3.3 GB with the dump (batch 0010). The generated Rust is the same
  but for the paths.
- **The format did not move with Burn.** Burn's revision went from `00a9db74` to `e8a6afbf` between batches 0010
  and 0011; the burnpack is the same size, and P10's numbers, derived at the older revision, hold at the new one.
- **The random part of a burnpack is 5,332 bytes.** 669 `param_id`s of 8 random bytes each: 669 × 8 × 255/256 is
  5,331. The data section is identical, so the content digests of two files are.
- **The Hub's revisions moved and the weights did not.** In all 20 commits of the Instruct repository, from
  2024-10-31 to 2025-09-22, `model.safetensors` has one id (`5af571cb…`); in the 9 commits of the base repository that
  have it, one (`80521b40…`). The tokenizer file `tokenizer.json` is the same blob in both repositories and in
  every commit. `config.json` has three ids in the Instruct repository and two in the base; `tokenizer_config.json`
  has three in the Instruct repository, and flips between two of them three times (`update model max`, `Update
  tokenizer`, `update model max`).
- **No repository that names the model holds the same file.** Of 39 found by searching for
  `SmolLM2-135M-Instruct`, 0 have the sha256 of the Hub's `model.safetensors`; the ones with a safetensors file of
  their own (`unsloth/`, `mlx-community/`, fine-tunes) have another. Whether any holds the same tensors in another
  file was not observed (it is observed in run 2).
- **The published `onnx/model.onnx`** (IR 7, opsets `""` 14 and `com.microsoft` 1, produced by
  `onnxruntime-genai`, 460 nodes, 276 initializers) **holds all 272 safetensors tensors**, 210 transposed and 62
  identical, and four more that no safetensors tensor has: `cos_cache` and `sin_cache` (`[8192, 32]`) and two integer
  constants. Its 211 `MatMul` nodes take 210 initializers and it has one `Transpose`, so the head is probably the embedding
  transposed in the graph. The record sees through a different exporter, a
  different opset and fused operators; what it adds is derived tables.
- **`accelerate` changes the graph and not the weights.** The same export with the package installed has 272
  initializers (the head is a `Transpose` of the embedding), 113 MB fewer bytes, and a sha256 of its own, and the
  same `bag_root`. Batch 0006's export, made with it, had 7,361 nodes and 272 constants for that reason.
- **The export is reproducible across three processors**: `7583ca8f…` on two of batch 0010's runs and on this one.
- **The tiny model's name pairing disagreed once**, for `lm_head`: the name transform reads `lm_head.weight` as the
  tied embedding, which is right for SmolLM2 and wrong for an untied model. The transform is a convention (an
  auxiliary), not the instrument.

### Limits

Two processor models, one model, a CPU, float32; the Hub's revision as of the runs. Hashes tell that two tensors are the
same, not why a model computes what it computes: the bag does not see wiring (P15 shows a binding error it cannot see)
and the weights that differ by a symmetry of the model have different keys. The ONNX Runtime and PyTorch forward passes
agreed to the bit across the two processors on every comparison here; that is two processors, not a guarantee. The
labelled root is stated for safetensors only. The name transform of P9 hard-codes the tie of `lm_head` to the
embedding and is wrong for an untied model (the tiny model's one disagreement).
