# Batch 0002: existing tools on sampled models

- **Registered:** 2026-10-05, before any cell ran.
- **Status:** run. All twelve cells have reported; cell 12 took three attempts. See Results.
- **Branch:** `batch/0002-existing-tools`. **Workflow:** `.github/workflows/batch-0002.yml`.

## Purpose

Programs that already run known-to-work language models exist. So do tools
that read, convert and describe such models. This batch runs twelve of them,
unmodified, on a small sample of models, to find out what each one gives,
what it needs, and where they disagree with one another.

The running programs are the baseline. Everything else in this project is to
be checked against them.

## Rules for this batch

- **No code of this repository's own.** Every step invokes an existing tool.
  What is hand-written is this document and the workflow's choice of tools,
  options and samples.
- **An observation is a workflow step marked `continue-on-error`.** Its
  recorded outcome, success or failure, is the result. A tool that fails on a
  sample has told us something.
- **A job fails only when setup fails:** an install or a download broke.
- **Tool runs go through GNU `time`,** so that what each one needs is on
  record before anything like it is run on a smaller machine.
- **Models are taken at their current revision.** Revisions and digests are
  recorded where a file is downloaded whole.
- **The prompt** is `The capital of France is`, as in batch 0001.

## Samples

- `HuggingFaceTB/SmolLM2-135M-Instruct`, and for configurations also the
  360M and 1.7B models of the same architecture.
- `openai-community/gpt2`, and for configurations also `gpt2-medium` and
  `distilbert/distilgpt2`.
- `Qwen/Qwen3-0.6B`, and for configurations also the 1.7B and 4B models; its
  published GGUF file `Qwen/Qwen3-0.6B-GGUF`.

## Cells

Baselines, programs that run a model:

- **05. llama.cpp on a published GGUF file.** Builds llama.cpp, loads
  `Qwen3-0.6B-Q8_0.gguf`, and records how it tokenises the prompt and the
  next token with its five most probable alternatives. `gguf-dump` records
  what the file says about itself.
- **06. llama.cpp on files it converted itself.** `convert_hf_to_gguf.py`
  turns the safetensors of GPT-2 and of SmolLM2-135M-Instruct into float32
  GGUF; llama.cpp then loads and runs each. Also records the list of
  architectures the converter knows.
- **08. Optimum's exporter.** `optimum-cli export onnx` builds an ONNX graph
  from the library's own definition of the model and compares its outputs
  with PyTorch's as part of the export. The `onnx` checker is then run on the
  result.

What a model's files say about themselves, without running it:

- **01. The Hub API.** Model information, files with sizes, and revision
  history for six repositories.
- **02. safetensors headers.** The tensor inventory of four models, read by
  range request without downloading weights.
- **07. Inspectors on published ONNX files.** The `onnx` checker, Polygraphy
  and onnxslim on the published SmolLM2 and GPT-2 graphs.

Schemas and code generated from samples:

- **03. quicktype.** From three configurations of each of three
  architectures: a JSON Schema per architecture, and Rust and Python types.
  The samples are then validated against the schema inferred from them.
- **04. schema-automator and LinkML.** From the same kind of samples: a
  LinkML schema, and from it OWL, SHACL, a JSON-LD context, JSON Schema and
  Python classes. The samples are validated against the schema.
- **10. ONNX's own schema.** `onnx.proto` to JSON Schema with a protoc
  plugin, then into LinkML, then OWL and SHACL.

Translations between representations:

- **09. ONNX2RDF.** A published graph to N-Quads, loaded into Oxigraph and
  counted by class.
- **11. IREE's ONNX importer.** Published graphs into MLIR.
- **12. ONNX Runtime's model builder.** Builds an ONNX graph for
  SmolLM2-135M-Instruct; the `onnx` checker is run on the result.

## Expected

- **03 and 04, controls.** GPT-2's configurations are validated against the
  schema inferred from the llama configurations. That step is expected to
  fail. If it passes, the inferred schema constrains nothing.
- **06.** For GPT-2, llama.cpp is expected to tokenise the prompt as batch
  0001 recorded (464, 3139, 286, 4881, 318) and to rank the same next tokens
  that PyTorch and ONNX Runtime did there (` the` 0.0846, ` now` 0.0479,
  ` a` 0.0462, ` France` 0.0324, ` Paris` 0.0322). A difference would be
  an error in one of three independent programs, or in the conversion.
- **07.** The checker rejects the published SmolLM2 graph and accepts the
  GPT-2 one, as in batch 0001.
- **08.** The exported graphs pass the checker.
- **12.** The builder's graph is rejected by the checker for the operator
  `SimplifiedLayerNormalization`. That would show where the operator in the
  published files comes from.
- **09, 10, 11.** No expectation. These are first contacts.

## Not in this batch

- **Introspection that exists only as a programming interface:** the loading
  report of `transformers`, building a model from its configuration alone,
  `torch.export`, TransformerLens. Calling them takes at least a line of
  code, and whether a line of invocation counts as configuration has not
  been decided.
- **A PyTorch baseline with token probabilities.** No command-line route was
  found; batch 0001's record is used.
- **Language frameworks** (K, SpecTec, IRDL).

## What was seen before registration

- Batch 0001's results.
- A web search on 2026-10-05, and the READMEs and sources of these tools,
  for what exists and how each is invoked.
- That the sample files exist on the Hub.
- No tool in this batch has been run on these samples.

## What this does not establish

- That a tool which succeeds here succeeds on other models.
- That two programs which agree on one prompt agree in general.
- Anything about tools not listed.

## Results

### Run 1: 2026-10-05

Workflow run [37316489676](https://github.com/metavacua/lm-normal-form/actions/runs/37316489676)
at commit `e1e511a`. Outcomes below are read from each job's log and
artifacts, not from the step list (see "How the run was recorded").

**Baselines**

- **05. llama.cpp on a published GGUF file: runs.** llama.cpp at revision
  `6c59c40` loads `Qwen3-0.6B-Q8_0.gguf`. It tokenises the prompt as 785,
  6722, 315, 9625, 374 and gives ` Paris` as the next token with
  probability 0.66, followed by ` located`, ` the`, `...` and ` ____`.
- **06. SmolLM2-135M-Instruct, converted and run: works.** The converter
  wrote a float32 GGUF from the safetensors in 4.5 s. llama.cpp tokenises
  the prompt as 504, 3575, 282, 4649, 314, with no BOS token, and gives
  ` Paris` 0.4695, ` the` 0.2657, ` located` 0.0831, ` called` 0.0176,
  ` Le` 0.0150.
- **06. The converted file describes the architecture.** It holds 272
  tensors, the number in the safetensors header, each under a role name
  (`token_embd`, `blk.0.attn_q`, `blk.0.attn_k`, `blk.0.attn_v`,
  `blk.0.attn_output`, `blk.0.ffn_gate`, `blk.0.ffn_up`, `blk.0.ffn_down`,
  `blk.0.attn_norm`, `blk.0.ffn_norm`). Its metadata gives 30 blocks, 9
  heads, 3 key/value heads, key and value length 64, embedding length 576,
  feed-forward length 1536, context length 8192, and the tokenizer's
  settings. These are the facts larql-cli-cpu #51 listed as not recoverable
  from headers.
- **06. GPT-2, converted: fails.** The converter stops with
  `Can not map tensor 'h.0.attn.bias'`. There is therefore no llama.cpp
  baseline for GPT-2, and the expectation for cell 06 was not evaluated.
  This names the twelve header tensors batch 0001 could not match: they are
  `h.N.attn.bias`.
- **08. Optimum's exporter: both exports pass the checker,** as expected.
  pip chose `transformers` 4.57.6 for Optimum 2.1.0.
- **08. Optimum's own comparison with PyTorch flags SmolLM2.** The largest
  difference is 3.0e-4 on the logits, against its tolerance of 1e-5; it
  reports the export as succeeded with a warning. GPT-2 raised no warning.
- **08. The exported SmolLM2 file is larger than the published one:**
  652,531,966 bytes against 540,345,794. The difference is close to one
  more copy of the embedding matrix; this was not checked by inspection.

**What files say about themselves**

- **01. The Hub API** returns revision, architecture name, file sizes,
  parameter totals and revision history for all six repositories. For the
  GGUF repository it also returns the architecture and context length read
  from the file.
- **02. safetensors headers** give 272, 290, 311 and 160 tensors for
  SmolLM2-135M, SmolLM2-360M, Qwen3-0.6B and GPT-2.
- **07. The checker** rejects the published SmolLM2 graph and accepts
  GPT-2's, as expected.
- **07. Polygraphy and onnxslim read both graphs** without asking the
  checker. onnxslim counts 1 `SimplifiedLayerNormalization` and 60
  `SkipSimplifiedLayerNormalization` nodes in the SmolLM2 graph. Polygraphy
  shows that the graph declares the `com.microsoft` operator set as well as
  ONNX's.

**Schemas and code from samples**

- **03. quicktype: works, and its control fails as it should.** From three
  llama configurations it infers 28 properties, 26 of them required, with
  the nested `transformers.js_config` object typed. The samples validate
  against it; GPT-2's configurations are rejected. It also wrote Rust and
  Python types.
- **04. schema-automator: the schema it infers rejects its own samples.**
  It types booleans as integers and a list and a nested object as strings.
  OWL, SHACL, a JSON-LD context and JSON Schema were generated from that
  schema all the same. The Python generator fails on the class name
  `Transformers.jsConfig`. The control is uninformative here.
- **10. ONNX's protobuf schema to JSON Schema: works** (192 files, four
  variants for each message). **Into LinkML: partial.** References between
  files are not resolved, and OWL generation then fails on an unknown
  range.

**Translations**

- **09. ONNX2RDF: works on both graphs.** GPT-2 becomes 127,913 quads, which
  Oxigraph loads. Its class counts include 3,095 nodes and 149 initializers,
  the same numbers batch 0001's hand-written emitter gave. SmolLM2 becomes
  54,053 quads; the non-standard operator is no obstacle.
- **11. IREE's importer: GPT-2 imports** into 1.3 GB of MLIR in 4 s.
  **SmolLM2 is refused,** because the importer runs the `onnx` checker first.
- **12. Not evaluated in this run.** The builder's `--help` crashes in
  Python's argument parser, and that call was in a setup step. The cell was
  run again by `.github/workflows/batch-0002-cell-12.yml`; see below.

**What the tools needed on the hosted runner** (peak memory of the largest
process, elapsed time)

- llama.cpp server build: 0.63 GiB per compiler process, 3.5 minutes on four
  cores.
- safetensors to GGUF: 0.51 GiB, 4.5 s. `gguf-dump` on a 639 MB file:
  0.51 GiB, 7 s.
- `onnx` checker on the 540 MB graph: 1.56 GiB, 1 s.
- Polygraphy: 1.05 to 1.26 GiB. onnxslim: 2.6 to 3.1 GiB.
- Optimum export: 2.8 GiB, 13 to 17 s.
- ONNX2RDF: 1.1 to 1.3 GiB.
- IREE import of GPT-2: 3.8 GiB, 4 s.

**Across cells**

- **Existing tools split on a graph the standard does not cover.** The
  checker and IREE's importer refuse the published SmolLM2 graph;
  Polygraphy, onnxslim and ONNX2RDF process it.
- **One tensor name stops two tools.** `h.N.attn.bias` is in GPT-2's
  safetensors, has no floating-point counterpart in the ONNX graph, and
  stops llama.cpp's converter.
- **One configuration key stops two tools.** `transformers.js_config`
  breaks LinkML's Python generator here, and is the key larql refused a
  model over.
- **An existing converter already assigns a role to every tensor** of a
  llama-type model and writes the architecture's dimensions.

**How the run was recorded**

- The step list reports every `continue-on-error` step as successful,
  whatever its exit status. Real outcomes had to be read from the logs. The
  rerun of cell 12 records them from the workflow's own `steps` context.
- The combined log omits jobs whose names contain a colon. Each job's log
  was fetched separately.

**Cell 12, run again**

Runs [37318184726](https://github.com/metavacua/lm-normal-form/actions/runs/37318184726)
and [37318381840](https://github.com/metavacua/lm-normal-form/actions/runs/37318381840).
The first of these stopped in the builder, which asks for a Hugging Face
login by default; the second switched that off with the builder's own option.

- **The builder's graph is rejected by the checker, as expected:**
  `No Op registered for SimplifiedLayerNormalization`, at the node
  `/model/layers.0/input_layernorm/LayerNorm`. That is the operator and the
  node name the checker reported for the published SmolLM2 file in batch
  0001.
- **Its operators match the published file's.** onnxslim counts 1
  `SimplifiedLayerNormalization`, 60 `SkipSimplifiedLayerNormalization` and
  30 `GroupQueryAttention` nodes, and reports the same model size, 515.13
  MB, for both. The published files were, on this evidence, made by this
  builder at an earlier version: the published graph is at opset 14, this
  one at opset 22.
- **The builder writes its own manifest of the model,** `genai_config.json`:
  type `llama`, 30 layers, 9 attention heads, 3 key/value heads, head size
  64, hidden size 576, context length 8192, vocabulary 49,152.
- **That manifest agrees with llama.cpp's.** Two programs that do not share
  code, reading the same weights, state the same architecture for
  SmolLM2-135M-Instruct. The published graph's own inputs agree as well:
  60 cached key/value tensors with 3 heads of dimension 64.
- **The builder's `--help` still crashes;** building does not need it.
- The build took 10 s and 0.92 GiB at peak.

**Not shown by this run**

- A second baseline for the next-token answers of SmolLM2 or Qwen3. Each has
  one program's answer and nothing to compare it with yet. Only the
  architecture facts of SmolLM2 have two independent sources so far.
- Whether llama.cpp's refusal of GPT-2 is intended or a fault at that
  revision.
