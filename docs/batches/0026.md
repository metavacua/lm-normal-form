## Purpose

Batch 0010 generated Rust from SmolLM2's ONNX graph with `burn-onnx` and ran
it natively with Burn's `flex` backend. The generated `model.rs` there
(793,128 bytes; 51,344 for the tiny graph) holds the structure and no weights;
the weights are a separate file, `model.bpk` (651,467,264 bytes), read through
a constructor. This batch asks what happens when the same graph is built for
`wasm32v1-none`, and where the first failure lands if there is one.

The target, as the rustc book describes it: Tier 2; `core` and `alloc` only,
no `std`; of the WebAssembly proposals after 1.0 only mutable globals is
enabled, and SIMD, bulk memory, sign extension, non-trapping float-to-int
conversion, multivalue, reference types and threads are not; compiled with
`-Cpanic=abort`. The book's page says nothing on linear-memory limits.

Existing work this batch is built on, not replaced:

- `burn-onnx`'s `ModelGen::load_strategy`. Its README lists four values.
  `File` is the default and is what batch 0010 used; it generates
  `from_file`, `from_bytes` and a `Default` that calls `from_file`. `Bytes`
  generates only `from_bytes(bytes, &device)` and is described there as good
  for "WebAssembly, custom loaders". `Embedded` compiles the weights into the
  binary with `include_bytes!`. The `onnx2burn` binary offers only `File` and
  `Embedded`; `Bytes` needs `ModelGen` called from a program.
- `burn-onnx`'s own example `examples/raspberry-pi-pico`: a `no_std` firmware
  on a Cortex-M33 whose README says the generated code "only needs `alloc`",
  that uses Burn's `flex` backend with the `critical-section` feature "for
  targets without atomic pointer support", and an existing allocator crate.
- Burn's README: "only the Flex backend can be used in a no_std environment",
  and Flex "runs on Wasm and no_std".

No part of the generated source is rewritten by hand or by a script written
for this batch.

## The claim it would license, and nothing more

If the predictions below hold, the Rust that `burn-onnx` generates from
Optimum's export of SmolLM2-135M-Instruct, with `LoadStrategy::Bytes`, can be
built for `wasm32v1-none` and, with its weights supplied as bytes, computes
what batch 0010's native build computes. It licenses nothing about a browser,
SIMD, threads, a GPU backend, the speed of the module beyond what is
observed, other models, other graphs, or any other Rust program.

## Cells

- **01 (one job, the inputs).** As batch 0010's cell 01: Optimum's export of
  both models without past; the prompts of `batches/0010/prompts.txt`;
  ONNX Runtime's logits with graph optimization on and off. The sha256 of each
  graph is recorded next to batch 0010's (run 37829130238: tiny
  `c777e479c9c071dfe82e412540d15107cbf2c8aabb096d8fcd27adad260cbccd`, SmolLM2
  `7583ca8fdc74af2ca98fb5cc254ea305f840ec3a2a1998c4be1f7c9a35a9df47`). A
  different digest is recorded and the new graph used; nothing in the claims
  depends on the digests being equal.
- **02 (generation).** `ModelGen` with `LoadStrategy::File` (as batch 0010),
  then with `LoadStrategy::Bytes`, on both graphs, at one recorded
  `burn-onnx` revision. Their `model.rs` files are kept with digests.
- **03 (the builds).** A `#![no_std]` crate with the `alloc` crate, Burn with
  default features off and the `flex` feature, `burn-store` without `std`, a
  panic handler and a global allocator, each an existing crate chosen from
  existing work and recorded before the code is written. Built for
  `wasm32v1-none` with `cargo build --release`, in this order: the `File`
  source of the tiny graph; the `Bytes` source of the tiny graph; the `Bytes`
  source of SmolLM2.
- **04 (the validator).** The `.wasm` of cell 03 is checked by an existing
  validator limited to the WebAssembly 1.0 feature set plus mutable globals.
  The tool and its flags are chosen from existing ones and recorded before the
  code is written.
- **05 (the run).** An existing WebAssembly runtime instantiates the module
  from cell 03; the host writes `model.bpk` into its linear memory and calls
  the module's entry point; the logits of every position of the three prompts
  are written and compared with those of ONNX Runtime and with batch 0010's
  native Rust logits by `batches/0010/compare.py`.

The prompts are batch 0010's, three, all raw continuations.

## Predictions, with severity

- **P1, a control, low severity.** The `File`-strategy source does not build
  for `wasm32v1-none`: the build fails with an error that names the crate
  `std`. Refuted if it builds, or if it fails with no error naming `std`.
  Batch 0010's `File` source contains `extern crate std;`, a `Default` that
  calls `from_file`, and a `from_file` using `std::path`; the book says the
  target has no `std`.
- **P2, low severity.** The `Bytes`-strategy source of each graph contains no
  `std::` path and no `extern crate std`. Refuted by one match. It is a text
  check of the generated files.
- **P3, high severity.** The `Bytes` source of the tiny graph builds for
  `wasm32v1-none` in the crate of cell 03. Refuted by any error from `rustc`
  or `cargo`. A refutation lands first on, in this order of suspicion: a
  dependency of `burn-store` that needs `std`; a dependency of the `flex`
  backend that needs `std` or threads; atomics (the pico example needs the
  `critical-section` feature on a target without atomic pointer support;
  whether this target does is not in the book's page); the allocator and the
  panic handler.
- **P4, moderate severity.** The `Bytes` source of SmolLM2 builds too, with
  the peak resident memory of `rustc` at most 2 GiB and the build at most 10
  minutes on the runner. Refuted by an error, or by either limit. Batch 0010's
  native build of this source took 8.48 seconds at a peak of 558,544 kB (its
  `outcomes.json`, run 37829130238); the limits are generous on purpose, and
  the size of the wasm module is observed.
- **P5, moderate severity.** The module of P4 validates under the validator of
  cell 04: it uses no instruction of a proposal that the book lists as off.
  Refuted by a rejection.
- **P6, high severity.** The module of P4, given SmolLM2's `model.bpk` by the
  host, runs the three prompts to the end with no trap, and its linear memory
  never exceeds 2 GiB. Refuted by a trap, a failed instantiation, or a larger
  memory. The weights alone are 621 MiB; the address space of `wasm32` is 4
  GiB.
- **P7, high severity.** For each prompt, the five most probable next tokens
  from the module are the same ids in the same order as ONNX Runtime's on the
  same graph and as batch 0010's native Rust, and each of the five
  probabilities differs by at most 1e-4. Refuted by another order or a larger
  difference.
- **P8, moderate severity.** The largest absolute difference of logits, over
  every position of every prompt and the whole vocabulary, is at most 1e-3
  against each of the two references. Refuted by a larger difference. If P7
  holds and P8 fails, the difference is numeric; where it enters is a later
  batch's question.
- **Control of the instrument.** `compare.py`, given logits with one value
  moved by 0.5, reports a largest difference of 0.5. Refuted if it does not.
- **Observed, no prediction.** The size of the `.wasm`; the build time and the
  peak memory of each build; the first error of each failed build and the
  crate it names; the number of crates; the peak linear memory and the time of
  one forward pass of each prompt, next to the native run of batch 0010 (0.51
  seconds elapsed for its runner on the SmolLM2 prompts, `outcomes.json`, run
  37829130238); whether the module imports anything beyond what the host
  provides.

## Auxiliaries

What a refutation could land on instead of the Rust itself, and which would be
blamed first:

- the choice and the version of the allocator, the panic handler and any
  critical-section crate (existing crates; the glue is the only code written
  for the build);
- the revision of `burn-onnx`, and the Burn revision its workspace names;
- the Rust toolchain and the installation of the target (recorded);
- the WebAssembly runtime and the host code that writes the weights into
  linear memory, including its page limits;
- the validator and its feature flags (P5);
- Burn's `flex` kernels on a target without SIMD, and its integer casts (the
  book lists non-trapping float-to-int conversion as off);
- ONNX Runtime's graph optimization, as in batch 0010's P5;
- `compare.py` (its control above).

## Rivals to exclude

- **The module is not what ran.** The digest of the `.wasm` is recorded and
  the runtime is given that file; the native run is a different file.
- **The weights are not the weights.** The digest of the `model.bpk` given to
  the host is recorded, and it is the file `ModelGen` wrote in cell 02.
- **A shared misreading of the graph.** Excluded for ONNX Runtime by batch
  0003 and 0010; here both references are compared.
- **Agreement on the last position only.** The logits of every position are
  compared.
- **The tiny graph.** It carries no claim; it is the smoke for what follows.
- **Not excluded:** padded inputs, cached inputs, other models, other
  graphs, other targets, threads, SIMD.
