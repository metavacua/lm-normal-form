## Purpose

An ONNX file declares versions in three places: an IR version for the file format, an opset version for each domain
of operators, and fields of its own (producer, model version, metadata). Whether any of them is a contract depends
on what reads them. A version that no reader checks is a label; one that a reader uses to choose an operator's
signature changes what the file means; one that two readers read differently makes the same file valid for one and
not for the other. The batch asks, for one file, which is which, with the readers the pipeline has: the checker
that ships with ONNX (`onnx.checker`), ONNX Runtime, the converter between opsets that ships with ONNX
(`onnx.version_converter`), and the exporter that writes the fields (Optimum with torch). The readers on the Rust
side (`onnx2burn`) and the other containers are a later batch's.

The predictions were read from source, not run: the researcher's notes on `onnx` 1.23.2, ONNX Runtime 1.30.0, torch
2.14.1 and optimum-onnx 0.1.0 give, for each change, what each reader should do and the line that does it. Where
the documentation says one thing and the code another, the prediction follows the code, and the row says so.

No LARQL code, text or data is used in this batch.

## The hypothesis, and what would refute it

**H.** For each version-bearing field of the ONNX file Optimum exports from SmolLM2-135M-Instruct, what the checker
and ONNX Runtime do with a change to the field (refuse, accept with the unchanged file's logits byte for byte, accept
with logits within 1e-4 and the same argmax) is what their source predicts, **including where the two readers
disagree**; and **no change to a version field makes a reader accept the file and compute something different** (the
logits beyond 1e-4, or another argmax).

The second half is the fail-closed property of a version field; the first is whether it can be predicted from source.
Each row of `predictions.tsv` is a test of the first; the second is refuted by one row observed `different`. A row is a
hit when the predicted class of each reader is the observed one and, for a refusal, one of the predicted fragments is
in the error. The observations of the Python and torch side of the export (the other seven rows) and of the saved graph
are graded the same way.

## The claim it would license, and nothing more

If the predictions hold, the version contracts of this ONNX file can be listed as declared, enforced or ignored by each
reader from source, and the table of which reader enforces which field (the document's findings) is a prediction that
survived a test, not a reading. It licenses nothing about other models, other exporters, other versions of the
readers (the table is for onnx 1.23.2 and ONNX Runtime 1.30.0), the CPU provider's neighbours (CUDA, others), or
the Rust-side readers.

## Predictions, with severity

Severity is how likely a row is to fail if H were false; the notes rate each row's risk (the chance that the source
reading is wrong) and rows rated medium or higher are the severe ones: 20 of 40 are medium, 2 medium-high, 1 high, 5
low-medium, 12 low. The predictions are the rows of `predictions.tsv`; these are the ones the document will be read by.

- **P1, low severity. The two ceilings differ.** IR 13: both accept, ONNX Runtime with the same logits (A1). IR 14: the
  checker accepts and ONNX Runtime refuses with `Unsupported model IR version: 14, max supported IR version: 13` (A2).
  IR 15: both refuse (A3). The field absent: both refuse (A4). Refuted by any other cell of these.
- **P2, moderate severity. ONNX Runtime does not enforce the IR floor.** IR 0 and IR 3: the checker refuses (`ir_version`
  not set; initializers not in the graph's inputs), ONNX Runtime accepts with the same logits (A5, A6). Refuted if it
  refuses either.
- **P3, low severity. A mislabelled opset is caught.** Opset 17, 13 and 12 on a graph that uses `ReduceMean` with axes as
  an input, `Reshape` with `allowzero` and `Unsqueeze` with axes as an input: both readers refuse, naming the older
  operator's schema (B1 to B3). Refuted by an acceptance. (This is what connects the version to what the file means.)
- **P4, moderate severity. An opset above the released ones.** 19 and 26: both accept, the logits the same with
  optimization off and within 1e-4 with it on (B4a to d). 27: the checker accepts and ONNX Runtime refuses (`under
  development`, `till opset 26`), and accepts with `ALLOW_RELEASED_ONNX_OPSET_ONLY=0` (B5, B5e). 28 and 100: it refuses,
  and with the gate off 28 is still refused, by the registry (B6 to B7). Refuted by any other.
- **P5, high severity. The spelling of the domain moves the gate.** `ai.onnx` 27 is accepted with the same logits while
  the empty domain's 27 is refused (B14b against B5); `ai.onnx` 99 is refused, later, by the registry (B14). Refuted if
  27 is refused when spelled `ai.onnx`.
- **P6, moderate severity. ONNX Runtime is more lenient than the checker, and stricter about what is declared.**
  No default-domain import with another domain present: the checker refuses, ONNX Runtime accepts, with the same logits,
  taking the last released opset (B9). An opset version of 2^32 + 18: the checker refuses, ONNX Runtime narrows it to
  18 (B8). An unused `ai.onnx.ml` 99: the checker accepts, ONNX Runtime refuses (B15). Two entries for one domain: the
  last wins in both (B12); the domain spelled twice (`""` 18 and `ai.onnx` 17): the checker accepts, ONNX Runtime refuses
  (B11). Refuted by any other.
- **P7, low severity. Fields that carry no version are inert; the readers differ at the edges.** `producer_*`, `domain`,
  `model_version`, `doc_string` and the graph name changed: both accept, same logits (C1). A field the schema has not
  got: both accept (C3). Two `metadata_props` with one key: the checker refuses, ONNX Runtime accepts (C2). Every
  node's domain spelled `ai.onnx`: the checker refuses, ONNX Runtime accepts (C4). An initializer twice: the checker
  refuses, ONNX Runtime accepts (C5).
- **P8, moderate severity. The converter.** To opset 17 and 16: it converts, the checker accepts the result and ONNX
  Runtime gives the same logits (D1, D2). To 14: it fails for want of an adapter (D3). To 19: it converts (D4). To 28: it
  converts and ONNX Runtime refuses (D4b). To 29: it fails (D5).
- **P9, low-medium severity. The exporter and its environment.** `--opset 19` and `20` write IR 9, `--opset 21` writes
  IR 10 and the exporter says that the highest opset it supports is 20; every one is accepted, with logits within
  1e-3 of the first export's. The export's sha256 is the first export's under another `PYTHONHASHSEED`, with one
  thread, and under `ATEN_CPU_CAPABILITY` `default` and `avx2` (E2 to E7).
- **P10, medium severity. The saved graph.** With optimization off: the IR version and producer are the original's, there
  is more than one opset import, no `Constant` node (they become initializers), more initializers than the original,
  and `noop_with_empty_axes` written out on `ReduceMean` (F1). With all of it: at least one node in `com.microsoft`, 30
  `QuickGelu`, and at most 61 default-domain `SimplifiedLayerNormalization` nodes (F2); the checker refuses the file if
  one is there (F3); ONNX Runtime accepts the file again and gives the logits of the session that saved it, byte for
  byte (F4). Refuted by any one.
- **P11, moderate severity. Fail closed.** No row of the matrix is observed `different`, for either reader, on any
  optimization level. Refuted by one.
- **Observed, no prediction.** The first lines of the error each reader gives (they are kept beside the prediction
  fragments); the time of each row; the tiny model's results (smoke).

## Auxiliaries

What a refutation could land on instead of H, and which would be blamed first:

- the changes: made by `onnx` (the protobuf message edited, then `onnx.save`), except the unknown field, which is
  appended as bytes, and the converter, which is `onnx.version_converter`;
- the first line of the error taken from ONNX Runtime's stderr (a warning could come last);
- the predictions' fragments, which are the notes' error texts and may differ in a word from what the readers say;
- the tiny graph, whose rows have the same operators but fewer nodes;
- ONNX Runtime's optimization level: where a row says `all`, the logits compared are those of the unchanged graph at
  that level; the optimizer chooses its fusions by opset, so within-floor differences on `all` are not a failure of H
  (the classes are `same/near`);
- the exporter's environment (the packages are as batch 0011's, and `accelerate` is not installed);
- the processor (batch 0010 and 0011 observed none that moved the export).

## Rivals to exclude

- **A refusal that is not about the version.** A row refused for a reason other than the field changed (the graph is
  broken another way) would count as a hit. The changes are chosen so that the graph is valid but for the field, and the
  error text is compared with the fragments.
- **An acceptance that is the field being ignored, and not tolerated.** A row accepted with the same logits is a field
  the reader did not use; where the notes say it is used (the opset for the operators' signatures), an acceptance of a
  change that a signature depends on refutes the prediction (P3).
- **A single graph.** The graph is the Optimum export; a graph of other operators could be read differently. The
  operators the graph uses whose signature changes between opsets are in the notes (`ReduceMean` 18, `Reshape` 14,
  `Unsqueeze` 13) and the rows use them.

#### The matrix: the class of every row is as predicted

accept or refuse, ONNX Runtime's same, near or refuse, the converter's success or failure. The harness reports 16 rows
as missed, and each is a miss of the **error-text fragments** only: it kept the last line of the checker's message, and
the first 300 characters of ONNX Runtime's, which end inside the path of the file before the sentence that names the
reason. No fragment could be seen; the texts are not graded in run 1. (The fault, and its amendment, are below.)

| refuses | refuses | A3, A4, B1, B2, B3, B10 (6) |

**The fail-closed property held.** No row was accepted with other logits: of 38 rows, ONNX Runtime accepted 23, and in
each of them its logits were **byte-identical** to the unchanged graph's (maximum difference 0), including opsets 19 and
26 with optimization on, where up to 1e-4 had been allowed. Nothing in the version fields of this file made a reader
compute something else. What differs between readers is what each refuses.

The high-risk rows came out as the source reading said: `ai.onnx` 27 is accepted while the empty spelling's 27 is
refused (B14b against B5), ONNX Runtime accepts an IR version of 0 and of 3, and takes opset 18 from a version of
2^32 + 18.

#### The exports and the saved graph

- **Exports** (E2 to E7, SmolLM2): `--opset 19` and `20` give IR 9, `--opset 21` gives IR 10 and the exporter said
  that the highest opset it supports is 20; each file has another sha256 and ONNX Runtime's logits on it are
  **byte-identical** to the first export's. With `PYTHONHASHSEED=1`, with one thread, and with `ATEN_CPU_CAPABILITY`
  `default` and `avx2`, the export has the first export's sha256. (The harness marked the three opset rows as missed
  on the logits: their class in `predictions-export.tsv` is `near`, which the document states as "within 1e-3" and
  which includes the same; see the amendments.)
- **The saved graph** (F1 to F4): with optimization off, the file has the original's IR version and producer, nine
  opset imports (the default and eight domains ONNX Runtime adds), no `Constant` node, 2,986 initializers (the 273 and
  the 2,713 constants), 4,524 nodes, and `noop_with_empty_axes` written out on `ReduceMean`. With all of it: 3,146
  nodes, 652 initializers, 60 nodes in `com.microsoft` (30 `QuickGelu`), and **61** default-domain
  `SimplifiedLayerNormalization` (the most predicted), which the checker refuses; ONNX Runtime accepts the file again and
  its logits are the saving session's, byte for byte. All predicted.

#### The first run's faults

- `onnx_matrix.py` kept `first_line` of each error: the last line of the checker's message and 300 characters of
  ONNX Runtime's. The checker's message begins with the schema's complaint and ends with the node it names; ONNX
  Runtime's begins with the path of the model. So the fragments of 16 rows were looked for in text that could not
  contain them. Their classes are right; their texts are not observed.
- The class of the three opset exports in `predictions-export.tsv` is `near`; the registered statement (P9) is "within
  1e-3 of the first export's", which the observed byte-identical logits satisfy, and the table's class was a narrower
  transcription of it. In `exports.py` a `same` now satisfies a predicted `near`.

#### Amendments before the second run

No prediction is changed. `onnx_matrix.py` keeps the whole of an error, on one line, but for ONNX Runtime's own
warnings, so that a fragment can be anywhere in it; `exports.py` reads a predicted `near` as same or near. The second
run grades the fragments.

### Limits

One graph, one pair of readers at one version each, the CPU provider; two processors in the two runs of this batch's
workflow, more in the batches before it. A row refused by both readers is refused for the reason in the text; the first
run did not read it.
